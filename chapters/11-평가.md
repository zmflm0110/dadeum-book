# 11장. 평가: 좋은지 어떻게 아는가

코드가 잘 돈다고 해서 엔진이 **좋은** 것은 아닙니다. "좋다"를 숫자로 재는 장치가 따로 필요합니다.
이 프로젝트는 코드의 상당 부분(`backend/eval/`, `backend/tests/`)이 이 장치입니다. 엔진 본체보다 평가 코드가 더 많습니다.

이 장의 모든 수치는 제가 **이 저장소를 받아 직접 돌려서** 얻은 값입니다(`python -m eval.pipeline`, 약 5분).

## 11.1 먼저 용어

| 용어 | 뜻 | 쉬운 말 |
|---|---|---|
| **정밀도(precision)** | 엔진이 "고쳐라"고 한 것 중 **실제로 맞게 고친** 비율 | 말한 것의 정확도 |
| **재현율(recall)** | 실제 오류 중 엔진이 **잡아낸** 비율 | 놓치지 않는 정도 |
| **오탐(FP, false positive)** | 맞는 글을 틀렸다고 함 | 헛짚음 |
| **미탐(FN)** | 틀린 글을 못 잡음 | 놓침 |
| **오탐률(FPR)** | 정문 중 엔진이 건드린 비율 | |
| **과교정** | 정문을 **틀리게 바꿔** 버림 | 오탐의 가장 나쁜 형태 |
| **정문** | 맞게 쓴 문장 | |
| **코퍼스** | 문장을 대량으로 모은 자료 | |

### 왜 두 숫자가 모두 필요한가

"전부 틀렸다고 하는" 엔진은 재현율이 100%지만 쓸 수 없습니다. "아무것도 안 건드리는" 엔진은 오탐이 0이지만 쓸모가 없습니다.
다듬은 **오탐을 훨씬 무겁게** 봅니다(1장 원칙). 그래서 하한을 오탐 쪽에 가장 엄격하게 겁니다.

## 11.2 평가 데이터 네 종류

| 데이터 | 규모 | 만드는 법 | 무엇을 재나 |
|---|---|---|---|
| `clean.jsonl` | 위키 정문 9,765 | 위키백과 문장 | 오탐·과교정 |
| `errors.jsonl` | 합성 오류 3,871 | 정문에 규칙으로 오류를 주입 | 재현율(카테고리별) |
| `gold.jsonl` | 225 | 국립국어원 규범 예문 | 규범과의 일치 |
| `casual_*.jsonl` | 구어 정문 3,000 / 오류 1,073 | nsmc 영화평 | 구어 도메인 |
| `real_errors/` | dev 300 · holdout 199 · holdout2 150 문장 | **사람이 실제로 쓴 문장**을 규범 기준으로 주석 | **실사용 재현율** |

### 합성 오류의 함정: 순환

합성 오류는 "규칙이 오류를 만들어 넣고, 규칙이 그것을 잡는" 구조입니다. 점수가 높게 나오지만 **규칙이 모르는 오류가 얼마나 있는지는 원리상 못 잽니다.**

> 2026-09-13 nsmc 구어 300문장을 규범 기준으로 직접 주석해 보니, 합성셋 로컬 재현율은 **93.8%**인데 실사용 오류의 자동교정 재현율은 약 **15%**였다.
> 놓친 것의 대부분은 소수 부류(의존명사 거/걸/건, 시간 명사 때·전·중, 부정 부사 안/못 …)에 몰려 있었다.

이 발견이 프로젝트의 방향을 바꿨습니다. "합성 점수를 올린다"가 아니라 **"실사용 오류를 잡는다"**가 기준이 됐습니다(13장).

### 실사용 평가셋의 구조 (`eval/real_errors/`)

파일 두 개가 한 세트입니다.

```
holdout_sentences.txt   한 줄에 한 문장
holdout_gold.txt        문장번호|||틀린부분|||고친부분|||부류      (한 행 = 편집 하나)

실제 예:
1|||전개 마저|||전개마저|||DEL
2|||재미 없었고|||재미없었고|||DEL
2|||별로 였다|||별로였다|||DEL
```

**부류 표기:** DN(의존명사), DET(관형사), EXV(있다/없다 합성), DEL(붙여쓰기), TN(시간명사), NEG(부정 부사), JOSA(조사), M-어휘·M-활용·M-구어(맞춤법 계열) 등.

### 점수를 매기는 법

한 오류마다:

1. 문장에서 `틀린부분`을 찾고, `고친부분`으로 바꾼 **기대 문장**을 만듭니다.
2. 엔진을 돌려 그 자리와 겹치고, **적용했을 때 기대 문장이 되는** 지적을 찾습니다(`hit`).
3. 그 지적이 **자동 교정 등급**(low가 아니고 제안이 있음)이면 `auto` 성공, 점선이라도 있으면 `any` 성공.

```python
hit  = [i for i in issues[sid] if i.start < w1 and i.end > w0 and _apply(text, i) == expected]
auto = any(_actionable(i) for i in hit)
```

여기서 `_actionable`의 사연이 있습니다.

```python
# 제안이 **빈 문자열**인 것은 공백을 지우는 교정이다(붙여 쓰기). 이걸 bool(s) 로 걸러 내는 바람에
# 붙여쓰기 교정이 전부 '저신뢰만' 으로 찍혀 DEL 부류가 실제보다 낮게 나왔다(29% vs 실제 79%).
if iss.confidence == "low" or not iss.suggestions: return False
return iss.suggestions[0] != iss.original
```

**빈 문자열 `""`은 "공백 삭제"라는 정당한 교정**인데, 파이썬에서 빈 문자열은 거짓(False)처럼 취급됩니다. `if suggestion:`처럼 쓰면 "제안 없음"과 구분이 안 됩니다. 이 사소한 차이로 한 부류의 점수가 29%로 찍혔고 실제는 79%였습니다.
**교훈:** 측정 도구의 버그는 엔진의 버그보다 오래 숨습니다.

## 11.3 실제 결과 (제가 돌린 값)

### 실사용 오류 재현율

| 평가셋 | 오류 수 | 자동 교정 | 점선 포함 |
|---|---|---|---|
| dev (300문장) | 356 | **265 (74%)** | 287 (81%) |
| holdout (199문장) | 204 | **146 (72%)** | 153 (75%) |
| holdout2 (150문장) | 178 | **120 (67%)** | 129 (72%) |

**주의:** README는 holdout2를 **63%**로 적고 있습니다(2026-09-17 측정). 제 환경에서 지금 돌린 값은 **67%**입니다. 4%p 차이의 원인은 확인하지 않았습니다(환경에서 켜진 층, README 이후의 변경 등이 후보). 다음 절의 "층이 켜졌는가"가 그 후보 중 하나입니다.

### 세 평가셋을 따로 두는 이유

> holdout은 규칙을 만들기 **전에** 주석하고 봉인했지만 그 뒤로 여러 번 들여다봤습니다. holdout2는 **처음 보는** 문장입니다.
> 세 수의 차이가 곧 **과적합의 크기**이고, 앞으로의 개선은 holdout2에서 주장합니다.

**과적합**은 "내가 본 문제에는 강하지만 새 문제에는 약한" 상태입니다. 시험 문제를 알고 공부하면 그 시험 성적이 좋아지는 것과 같습니다.
dev(74%)는 규칙을 만들 때 계속 보는 셋이라 가장 높고, 처음 보는 문장인 holdout2(67%)가 실제 실력에 가장 가깝습니다.

### 부류별로 보면 (dev 기준 일부)

| 부류 | 오류 | 자동교정 | 비고 |
|---|---|---|---|
| DN 의존명사 | 71 | 94% | 가장 많이 잡음 |
| TN 시간명사 | 24 | 88% | |
| EXV 있다/없다 | 37 | 73% | |
| OTH 기타 | 29 | **34%** | 가장 약함 |
| M-구어 | 8 | 38% | 구어 표기 |
| JOSA 조사 | 28 | 57% (점선 포함 86%) | 조사는 점선으로 많이 잡힘 |

### 오탐 후보 목록

평가는 "정답과 안 맞는 자동교정"도 출력합니다. dev에서 15건이었습니다. 몇 가지 예:

```
#41  '나' → ' 나'   [noun_verb_space_rule]
#132 '써져' → '쓰여' [dict_rule]
#224 '않' → '안'    [ml_confusion]
#276 '다르게 보이네요' → '다르게 보인다' [consistency_rule]
```

이것은 **오탐이 확정된 목록이 아닙니다.** "주석에 없는 교정"이라서, 진짜 오탐일 수도 있고 **주석자가 놓친 진짜 오류**일 수도 있습니다. 사람이 하나씩 읽어 갈라야 합니다.

## 11.4 품질 파이프라인: `python -m eval.pipeline`

모든 변경이 이 한 명령을 통과해야 합니다. **순서가 설계**입니다.

```
[layers]        어느 층이 켜졌나
[per-rule fpr]  어느 규칙이 정문을 건드리나
[coverage]      그 구문을 재고는 있나
단위테스트      1,020개
모델·사전 대조  배포본이 원본과 같은 값을 내나
QA 게이트       불변식 · 회귀 · 코퍼스 스캔 · 퍼즈
메트릭 하한     문어 6개 · 구어 1개
```

실제로 돌렸을 때의 요약입니다.

```
✓ unit-tests      1020 passed in 37.6s
✓ model-export    .ddm이 sklearn 원본과 일치
✓ lexicon         어절 1,806,050개 · 21.7MB
✓ qa-gates
✓ metric-floors
✓ casual-floors
파이프라인 통과 (308.9s)
```

### 단계 ① `[layers]`: 어느 층이 켜졌나를 먼저 찍는다

```
ok  띄어쓰기 태거(BiGRU)
ok  C 경로(이상탐지)
ok  1층 규칙 · 2층 혼동쌍 · D 문체
```

**이유:** 모델 파일이나 의존성이 없으면 그 층은 조용히 빠집니다(앱이 죽지 않게 하는 설계). 그러면 지표는 **"다른 엔진"을 잰 값**이 됩니다. 실제로 CI가 torch 없이 돌면서 태거 없는 파이프라인을 재고 있던 일이 있었습니다(2026-08-30). 그 뒤로는 실행마다 어느 층이 켜졌는지 먼저 찍습니다.

### 단계 ② `[per-rule fpr]`: 규칙별 오탐률

전체 오탐률은 규칙 수백 개를 한 숫자로 뭉갭니다. 그래서 **규칙마다 자기 표본에서만** 따로 잽니다.

```
전체 fpr           9 / 10,000 = 0.0009
confusion:den      4 /     30 = 0.133     ← 같은 엔진, 148배
```

희석이 사라지면 값이 전혀 다르게 보입니다. 실제 결과의 일부:

```
ok  checker:compound_space_rule     3/30 = 0.100
ok  checker:yul_ryul_rule           2/30 = 0.067
ok  confusion:doe                   0/30 = 0.000  (상한 <= 0.050)
ok  checker:boundary_model          0/30 = 0.000  (상한 <= 0.050)
```

위 두 줄(0.100, 0.067)은 숫자만 보면 높아 보입니다. 이 규칙들은 **상한이 등록되지 않아** 값을 보고만 하고 게이트하지 않으므로 `ok`로 찍힙니다. 실제 출력은 발동한 문장을 같이 보여 주는데(`종류에 관계 없이…`처럼 원문이 `관계없이`를 띄어 쓴 경우가 보입니다), **세 건이 모두 원문의 진짜 오류인지는 제가 하나씩 읽어 확인하지 않았습니다.** 이런 줄을 사람이 읽어 갈라야 한다는 것이 이 단계의 요점입니다.

#### 표본이 부족하면 숫자를 내지 않는다

```
insufficient_sample 36개 (표본 < 20) — 수치를 내지 않는다
0% 가 아니라 '못 쟀다' 이다.
```

**0%와 "못 쟀다"는 전혀 다른 말**인데, 숫자로 뭉개면 후자가 전자로 읽힙니다. 그래서 표본이 20건 미만이면 숫자를 내지 않고 "사각지대"라고 적습니다.

### 단계 ③ `[coverage]`: 그 구문을 재고는 있나

```
ok  되/돼              1399건  (하한 >= 1300)
ok  안/않               378건  (하한 >= 180)
ok  연결어미 -되          2건  ← 코퍼스로는 못 잼(테스트가 지킴)
ok  율/률                23건  ← 코퍼스로는 못 잼(테스트가 지킴)
```

**이 게이트가 없어서 실제로 버그를 놓친 적이 있습니다.** 연결어미 `-되`(적되·하되)를 `돼`로 고치는 과교정이 medium으로 나가고 있었는데, 정문 10,000문장에 그 구문이 **1건**뿐이라 아무리 잘못 고쳐도 오탐률이 움직이지 않았습니다.
지표를 믿기 전에 **"그 구문의 정문 표본이 충분히 있는가"**를 먼저 봅니다. 없는 구문은 "코퍼스로는 못 잼, 테스트가 지킴"이라고 정직하게 적고, 대신 표적 단위 테스트를 연결합니다.

### 단계 ④ 단위 테스트 1,020개

테스트 파일이 검사기마다 하나씩 있습니다(`test_josa.py`, `test_tense.py`, `test_confusion.py` …). 구조는 모두 같습니다.

```python
def test_...():
    issues = check_xxx("틀린 문장", kiwi)
    assert issues[0].suggestions == ["고친 말"]

def test_..._is_never_flagged():
    assert check_xxx("맞는 문장", kiwi) == []      # 정문을 건드리지 않는다
```

"정문을 건드리지 않는다"는 테스트가 "잡는다"는 테스트만큼 많습니다.

### 단계 ⑤ 모델·사전 대조

```
model-export: .ddm이 sklearn 원본과 같은 확률을 내는가 (최대 오차 1e-12 이내)
lexicon:      어절 사전이 원본과 같은 횟수를 내는가
```

"배포본(`.ddm`)"과 "학습본(`.joblib`)"이 어긋나면 `meta.json`의 문턱이 **지금 돌지 않는 모델**을 설명하게 되므로 매번 대조합니다.

### 단계 ⑥ QA 게이트 (`eval/qa/`)

예시 한 개가 아니라 **불변식**을 겁니다. "어떤 입력이어도 이것만은 참이어야 한다"는 규칙입니다.

| 불변식 | 내용 | 실행 결과 |
|---|---|---|
| **P1 무악화** | 자동 교정을 적용하면 형태소 분석이 나빠지지 않는다(모르는 형태소가 늘지 않음) | 위반 0 |
| **P2 멱등** | 고치고 다시 검사해 또 고쳐도 더 이상 안 바뀐다 | 위반 0 |
| **P3 정문 침묵** | 정문 코퍼스에서 high가 거의 0 | 오탐 0건 |
| **P4 편집 최소성** | 교정이 원문과 너무 멀리 가지 않는다(`면→수면` 같은 도약 금지) | 위반 0 |
| **P5 문맥 불변** | 문장 하나에서 찾은 교정은 그 문장이 문서 속에 있어도 똑같이 찾아진다 | (코드 수준 불변식) |

그 밖에:

```
[회귀 스위트] 등록 22건, 실패 0건
[코퍼스 스캔] 3000문장, high-conf 오탐 0건
[퍼즈]        500문장 변형 ...
```

- **회귀 레지스트리(`regressions.jsonl`, 22건):** 과거에 틀리게 고쳤던 문장을 영구 등록해 "다시는 안 틀린다"를 게이트로 둡니다. 형식은 `{"sentence": ..., "mode": "absent", "original": "든", "suggestion": "던", "note": "foreign proper-noun mis-parse (세든->세던)"}`. `absent`는 "이 교정이 나오면 안 된다"입니다.
- **퍼즈(fuzz):** 정문에 무작위로 오류를 주입해(`add_space`, `delete_char`, `keyboard` …) 검출률을 봅니다.

| 변형 | 검출률 | 의미 |
|---|---|---|
| an_anh | 100% | 안/않 바꾸기는 다 잡음 |
| doe_dwae | 94% | |
| josa_swap | 58% | |
| add_space | 35% | |
| delete_char | 4.6% | 글자 하나 빠짐은 거의 못 잡음 |
| dup_char | 3.2% | 글자 중복은 거의 못 잡음 |
| keyboard | 7.2% | 자판 오타 |

**낮은 수치를 숨기지 않습니다.** 이 표가 엔진의 약점 지도입니다. `delete_char`·`dup_char`가 낮은 것은 9장 끝의 "음절 하나를 빼려면 단어를 알아야 한다"는 한계와 같은 이야기입니다.

### 단계 ⑦ 메트릭 하한(floors)

```
ok  precision            0.9921  (floor >= 0.97)
ok  fpr                  0.0000  (floor <= 0.002)
ok  over_correction_rate 0.0000  (floor <= 0.002)
ok  l1_recall            0.9791  (floor >= 0.97)
ok  l2_recall            0.9924  (floor >= 0.99)
ok  roseo_recall         0.8503  (floor >= 0.82)
```

| 지표 | 하한 | 실측 | 뜻 |
|---|---|---|---|
| precision | ≥ 0.97 | 0.9921 | 고친 것 중 맞은 비율 |
| fpr | ≤ 0.002 | 0.0000 | 정문을 건드린 비율 |
| over_correction_rate | ≤ 0.002 | 0.0000 | 정문을 **틀리게 바꾼** 비율 |
| l1_recall | ≥ 0.97 | 0.9791 | 규칙 층이 잡는 비율 |
| l2_recall | ≥ 0.99 | 0.9924 | 혼동쌍 모델 층 |
| roseo_recall | ≥ 0.82 | 0.8503 | 로서/로써 |

**하한은 후퇴 금지선입니다.** 코드 주석의 뜻(의역): 엔진이 좋아지면 올리고, 변경을 통과시키려고 **내리지 마라.**
**하한은 품질 목표가 아닙니다.** "여기서 더 나빠지면 안 된다"일 뿐 "여기까지면 충분하다"가 아닙니다.

#### 하한 하나를 폐기한 일

처음엔 `l3_recall`(계층 가중평균)로 걸었다가 걷어냈습니다. 성격이 전혀 다른 두 집단(합성 roseo 0.83 vs gold의 문맥·시제 0.013)을 섞기 때문에 **성능이 그대로여도 구성비만 바뀌면 값이 움직였기** 때문입니다(0.6768 → 0.5850, 그런데 같은 엔진의 roseo 재현율은 0.8205 → 0.8305로 오히려 올랐음). **구성비에 흔들리는 하한은 회귀 방지선 노릇을 못 합니다.** 카테고리 단위로 바꿨습니다.

### 단계 ⑧ 구어 도메인은 따로 잰다

```
casual 정문 2,936 · 오류 1,073
  precision      0.3096
  recall         0.9515
  casual_fpr     0.3835
  raw_touch_rate 0.3967   (<= 0.40)
```

**구어 정밀도·오탐률은 하한이 걸려 있지 않습니다.** 이 값이 재는 것은 엔진이 아니라 **코퍼스**이기 때문입니다.

> 띄어쓰기 규칙이 들어오기 전 구어 과교정률은 1.84%였는데 규칙이 들어오자 31%로 뛰었다. 발동한 것을 무작위로 뽑아 읽으니 **20건 중 19건이 원문의 진짜 띄어쓰기 오류**였다(`웃긴부분은`, `높은거지`, `남편때문에`).
> nsmc의 "정문"은 오류를 주입하지 않았다는 뜻일 뿐, 띄어쓰기를 지켰다는 뜻이 아니다.

그래서 구어에서 게이트로 거는 값은 **사람이 실제로 보는 지적 빈도**(`raw_touch_rate` ≤ 0.40, 측정 0.3967)입니다. "두 문장 반에 하나꼴로 밑줄이 뜬다"는 뜻이고, 그것을 낮출지 말지는 **측정이 아니라 제품 결정**이라고 문서가 못 박고 있습니다.

## 11.5 이 장의 교훈 정리

| 교훈 | 근거 사건 |
|---|---|
| 측정이 정확해질수록 지표가 **나빠** 보일 수 있다 | 빈 제안(공백 삭제)을 자동교정으로 세지 않던 버그 수정 후 구어 지적률 .3543 → .3860 |
| 평균 하나는 결함을 희석한다 | 전체 fpr 0.0009 vs `den` 0.133 |
| "0%"와 "못 쟀다"는 다르다 | 표본 20건 미만이면 수치를 내지 않음 |
| 재고가 없으면 지표를 믿지 말라 | 연결어미 `-되` 표본 1건 |
| 규칙이 만든 시험은 규칙을 칭찬한다 | 합성 93.8% vs 실사용 15% |
| 시험을 본 사람은 점수가 부풀려진다 | dev 74% → holdout 72% → holdout2 67% |
| 측정 도구도 코드다 | 빈 문자열 버그 29% vs 79% |
| 같은 것을 두 길로 재면 서로 대조하라 | `style` 카테고리 500 사건 |
