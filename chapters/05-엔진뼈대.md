# 5장. 엔진 뼈대: 후보를 모으고 정리하는 구조

6~10장에서 개별 검사기를 하나씩 봅니다. 그 전에 **검사기들을 감싸는 틀**을 이해해야 합니다.
이 틀이 `backend/app/engine.py`(183줄)와 `backend/app/checkers/base.py`, `sources.py`입니다.

## 5.1 한 문장으로

> **검사기 21개가 각자 "여기 틀린 것 같다"는 후보를 내면, 겹치는 후보를 우선순위로 정리해서 한 목록으로 돌려준다.**

```
문장 ─▶ ① 분석 ─▶ ② 후보 ─▶ ③ 병합 ─▶ 지적 목록
```

## 5.2 왜 "하나의 흐름"인가: 만들어진 이유

`engine.py` 맨 위 설명문에 이유가 적혀 있습니다.

> 이 흐름이 예전엔 두 군데에 따로 적혀 있었다: `app/api.py`의 `/check`와 `eval/qa/common.py`의 `run_local`.
> 한쪽에만 검사기를 더한 채로 어긋나, **문체 일관성 재현율이 평가에서 0으로 찍힌 적이 있다**(측정 도구가 제품과 다른 코드를 밟았다).

즉 "제품이 돌리는 길"과 "성적을 재는 길"이 서로 다른 복사본이었습니다. 제품에는 검사기를 넣었는데 평가 쪽에는 안 넣어서, 평가는 "그 검사기는 아무것도 못 잡는다"고 보고했습니다.
지금은 둘 다 `engine.analyze()` 한 함수만 부릅니다. **검사기를 더하거나 빼는 곳이 `GENERATORS` 목록 한 줄**입니다.

> 이 원칙의 뿌리는 4장에서 본 `style` 사건과 같습니다. "재는 길과 쓰는 길이 같아야 한다."

## 5.3 자료: `RawIssue`

모든 검사기가 같은 모양으로 후보를 냅니다(`checkers/base.py`).

| 필드 | 뜻 | 예 |
|---|---|---|
| `start`, `end` | 원문 위치 `[start, end)` | `2`, `3` |
| `category` | 종류 | `josa` |
| `source` | 어느 규칙이 냈나 | `josa_rule` |
| `original` | 원문의 그 부분 | `을` |
| `suggestions` | 고칠 말 목록 (비어 있을 수 있음) | `["를"]` |
| `message` | 사람에게 보여 줄 설명 | |
| `confidence` | `high` / `medium` / `low` | `high` |

**`suggestions`가 비어 있다**는 것은 "여기가 수상하다"만 말하고 고칠 말은 없다는 뜻입니다. 이상탐지, 문체 일관성이 그렇습니다.

## 5.4 검사기 등록: `GENERATORS`

```python
@dataclass(frozen=True)
class Generator:
    name: str
    layer: int      # 1 = 규칙·로컬 모델, 2 = 혼동쌍 분류기
    run: Callable[[str, object], list[RawIssue]]

GENERATORS = [
    Generator("spacing", 1, check_spacing),
    Generator("dictionary", 1, lambda t, k: check_dictionary(t)),
    Generator("morph", 1, check_morph_rules),
    Generator("josa", 1, check_josa),
    Generator("jamo", 1, check_jamo),
    ...
    Generator("confusion", 2, lambda t, k: check_confusion(t)),
    Generator("boundary", 2, check_boundary),
]
```

모든 검사기는 **같은 약속**을 지킵니다: `(글, Kiwi) → 후보 목록`.
어떤 검사기는 Kiwi가 필요 없어서 `lambda t, k: check_dictionary(t)`처럼 `k`를 버립니다.

`layer`는 소요 시간을 층별로 나눠 재기 위한 꼬리표입니다(응답의 `elapsed_ms`).
이름이 "2층"이지만 실행 순서가 아니라 **분류**입니다. 목록 순서대로 하나씩 실행됩니다.

## 5.5 `analyze()` 한 줄씩

```python
def analyze(text, use_l2=True):
    shared = _SharedAnalysis(_kiwi)
    candidates = []
    elapsed = {1: 0.0, 2: 0.0}
    for gen in GENERATORS:
        if gen.layer == 2 and not use_l2:
            continue
        t0 = perf_counter()
        candidates += gen.run(text, shared)
        elapsed[gen.layer] += perf_counter() - t0
    return Analysis(
        issues=merge_and_dedupe(candidates),
        elapsed_ms={"layer1": ..., "layer2": ...},
    )
```

1. `_SharedAnalysis(_kiwi)`: 이 요청 동안만 쓰는 분석 공유 캐시(3장).
2. `for gen in GENERATORS`: 검사기를 **등록된 순서대로** 하나씩.
3. `candidates += gen.run(text, shared)`: 후보를 한 바구니에 쏟아 넣습니다. 이 시점에는 정리하지 않습니다.
4. `perf_counter()`: 시계. 실행 전후를 재서 층별 시간을 모읍니다.
5. 마지막에 `merge_and_dedupe`로 한 번에 정리합니다.

`use_l2=False`로 2층을 끄고 1층만 돌릴 수 있습니다(평가에서 층별 기여를 따로 재기 위해).

> **순서는 동작의 일부입니다.** 병합은 "같은 자리·같은 길이면 먼저 온 쪽이 남는" 안정 정렬이라서, 목록 순서를 바꾸면 출력이 바뀝니다. 그래서 목록 순서도 코드의 일부로 취급합니다.

## 5.6 병합: `merge_and_dedupe` (엔진의 심장)

검사기들은 서로를 모릅니다. 그래서 같은 자리를 둘 이상이 지적하는 일이 흔합니다.
예문 `안되요`에서는 사전 규칙이 `되요→돼요`를, 혼동쌍 모델이 `되→돼`를 같은 자리에 냈습니다.
둘 다 보여 주면 겹친 밑줄이 되므로 **하나만** 남깁니다.

### 알고리즘

```python
ordered = sorted(issues, key=lambda i: (i.start, -(i.end - i.start)))
kept = []
cursor = -1
for issue in ordered:
    if issue.start >= cursor:           # 앞의 것과 안 겹침
        kept.append(issue); cursor = issue.end
        continue
    prev = kept[-1]                      # 겹침 → 승부
    if _has_fix(issue) != _has_fix(prev):
        if _has_fix(issue):
            kept[-1] = issue; cursor = issue.end
        continue                         # (제안 있는 쪽이 이김)
    if SOURCE_PRIORITY[issue.source] > SOURCE_PRIORITY[prev.source]:
        kept[-1] = issue; cursor = issue.end
return _drop_noise_adjacent_to_fixed_typos(kept)
```

### 규칙을 말로 풀면

1. **정렬**: 시작 위치가 빠른 순, 같으면 긴 것 먼저.
2. 하나씩 보면서, 직전에 남긴 것과 **안 겹치면 남깁니다.**
3. **겹치면 승부**:
   - **(가)** 한쪽만 고칠 말이 있으면 → **고칠 말이 있는 쪽**이 이긴다.
   - **(나)** 둘 다 있거나 둘 다 없으면 → **출처 우선순위 숫자가 큰 쪽**.
   - **(다)** 우선순위도 같으면 → **먼저 온 쪽**이 남는다(바꾸지 않으므로).

### 여섯 가지 상황을 직접 돌려 본 결과

| # | 입력 | 결과 | 이유 |
|---|---|---|---|
| 1 | `(0-2 dict)` `(5-7 josa)` | 둘 다 남음 | 안 겹침 |
| 2 | `(26-28 dict, 제안)` `(26-27 ml_confusion, 제안)` | **dict** | 둘 다 제안, 우선순위 5 > 4 |
| 3 | `(30-32 anomaly, 제안 없음)` `(30-32 typo, 제안 있음)` | **typo** | (가) 제안 있는 쪽 |
| 4 | `(0-2 kiwi_space)` `(0-2 tagger_space)` | **kiwi_space** | 우선순위 0 = 0, 먼저 온 쪽 |
| 5 | `(2-3 josa)` `(0-5 dict)` | **(0-5 dict)** | 긴 쪽이 먼저 정렬됨, josa(2)는 dict(5)에 짐 |
| 6 | `(0-3 dict 희한, high)` `(3-4 kiwi_space, medium)` | **dict만** | 아래 5.8 |

### 왜 "제안 있는 쪽이 먼저"인가 — 실제 사고

코드 주석(2026-08-30)입니다.

> 교정을 만들지 않는 층(이상탐지, 문체 일관성)은 "여기가 수상하다"만 말한다. 그런 지적이 어절 전체를 덮으면 그 안의 진짜 교정을 밀어낼 수 있다. 실제로 그랬다: **`자률신경`을 이상탐지가 통째로 잡아 `률→율` 교정이 사라졌고** 회귀 레지스트리가 그걸 잡아냈다. 우선순위 숫자만으로는 못 막는다. **조언은 교정에 양보한다.**

이상탐지의 우선순위가 0이고 `yul_ryul_rule`도 0이라 숫자만으로는 비길 때가 있었던 것입니다. 그래서 "숫자 비교 이전에 제안 유무로 먼저 가른다"는 규칙이 앞에 들어갔습니다.

## 5.7 출처 우선순위표: `sources.py`

58개 출처가 한 표에 적혀 있습니다. 구조는 이렇습니다.

```python
@dataclass(frozen=True)
class Source:
    name: str       # "josa_rule"
    layer: str      # "rule" | "model" | "advice"
    priority: int
    basis: str      # 근거 설명
```

### 층(layer)의 뜻

| 층 | 뜻 |
|---|---|
| `rule` | 결정적 규칙. 같은 입력이면 늘 같은 출력 |
| `model` | 통계·학습 모델 (혼동쌍, 태거, 경계 판정기 등) |
| `advice` | 교정을 만들지 않고 "확인해 보라"만 말함 |

### 우선순위

| 값 | 출처 | 이유 |
|---|---|---|
| **6** | jamo, quotation, honorific, animacy, negative_polarity, tense, causative, agreement | 문법 규칙이 문맥을 보고 확정한 것. 가장 특수하고 신뢰 높음 |
| **5** | dict_rule | 국립국어원 기준 사전 규칙 |
| **4** | ml_confusion | 혼동쌍 학습 모델 (형태론 확정 포함) |
| **3** | dependent_noun_rule, particle_spacing_rule | 의존명사·조사 붙이기 |
| **2** | josa_rule | 받침 조사 |
| **1** | typo_rule, boundary_model | 오타·경계 모델 |
| **0** | 나머지 (띄어쓰기 세부 규칙 대부분, kiwi_space, tagger_space, consistency, anomaly) | 기본값 |

원칙: **"더 특수하고 더 선별된 근거가 일반적인 것을 이긴다."**

### 표 없이 쓰던 시절의 사고

`sources.py` 맨 위 주석입니다.

> 예전에는 우선순위가 `base.py`의 딕셔너리에만 있었고, 2026-09-13에 추가한 띄어쓰기 규칙 11종은 **그 표에 없는 채로 기본값 0으로 돌았다.**
> 출처를 더하는 곳을 한 군데로 모으고, **표에 없는 출처가 나오면 테스트가 실패하게 했다**(`tests/test_engine.py`).

"규칙을 더했는데 우선순위를 안 적어서 조용히 0이 된" 사고입니다. 기본값에 의존하면 아무도 모르게 틀립니다. 그래서 **"모르는 출처가 나오면 시끄럽게 실패"**로 바꿨습니다.

```python
def priority(name):
    s = SOURCES.get(name)
    return s.priority if s else 0
```

(이 함수 자체는 여전히 기본값 0을 주지만, 테스트가 "엔진이 내는 모든 source가 표에 있다"를 검증합니다.)

## 5.8 마지막 청소: `_drop_noise_adjacent_to_fixed_typos`

```python
anchors = [i for i in issues if i.source == "dict_rule" and i.confidence == "high" and i.suggestions]
return [issue for issue in issues
        if not (issue.source in ("kiwi_space", "tagger_space", "kiwi_typo")
                and issue.confidence != "high"
                and any(issue.start == a.end or issue.end == a.start for a in anchors))]
```

**상황:** `희안하게`는 맞춤법 오류(`희한하게`)입니다. 사전 규칙이 `희안→희한`을 high로 잡습니다.
그런데 틀린 철자 때문에 Kiwi가 이 단어를 엉뚱하게 해석해서 바로 옆에 "`하`를 따로 띄우자"는 쓸데없는 제안이 같이 나옵니다.

**해결:** 확실한 사전 규칙 교정의 **바로 옆에 붙어 있는** 애매한 띄어쓰기·오타 후보는 버립니다. 맞춤법을 고치고 나면 그 전제(틀린 철자)가 사라지므로 쓸데없는 제안이 되기 때문입니다.
`i.start == a.end or i.end == a.start`는 "앞뒤로 딱 붙어 있다"를 뜻합니다.

빠진 두 개:

- `(30-32 매읽, anomaly)`: `typo_rule`이 고칠 말을 가졌으므로 탈락(가).

### 한 가지 눈여겨볼 점: 서로 다른 길이 같은 곳을 가리킨다

`안되요`는 두 가지가 동시에 맞습니다: `안` 뒤에 공백(`안 되요`)과 `되요→돼요`. 둘은 위치가 달라서(25-26, 26-28) 겹치지 않고 **둘 다 남습니다.**
"모두 고치기"가 앞에서부터 하나씩 적용하면 `안 돼요`가 됩니다(12장).

## 5.10 확인 문제

1. 겹치는 두 후보가 모두 제안이 있고 우선순위가 같으면? (먼저 정렬된 것이 남음, 정렬 키는 시작 위치·긴 것 먼저)
2. 이상탐지(제안 없음, 우선순위 0)가 사전 규칙(제안 있음)과 겹치면 누가 이기나? (사전 규칙. 우선순위 비교 이전에 "제안 있음"이 이긴다)
3. `GENERATORS`의 순서를 바꾸면 안 되는 이유? (같은 자리·같은 길이·같은 우선순위일 때 먼저 온 쪽이 남기 때문)
